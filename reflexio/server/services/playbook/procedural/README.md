# Procedural playbook extraction

The selected method reads source-linked observations, compiles complete inert
skill documents and independently reviews every complete resulting unit. Code
accepts only complete passing related-change groups. A genuine empty reader
batch avoids compilation and review. `workflow.py` and the contracts have no
storage or publication authority.

`native.py` runs the method inside the existing window coordinator. It journals
completed stages, freezes actual preferred profiles and resolved model ladders,
keeps physical reservations charged across worker restarts, and returns an
ordinary native `PlaybookWritePlan`. A retirement-only plan is meaningful despite
having no new rows. The native publisher owns locks, atomic writes, lineage,
billing and post-commit aggregation. It validates the exact retained reviewed
plan and original source/historical witnesses before writing. No model
reconciliation or post-review DocumentExpander runs after this selected method.
Typed terminal model-contract failures are retained and re-raised, including
explicit incomplete batches; restarting a worker cannot redraw them as a repair.
Provider outages, turn suspension and actual embedding exceptions keep their
native retry behavior. The current journal retains physical usage/provenance and
completed parsed stage outputs, not a claimed archive of every raw provider body.

`inline.py` uses the existing initial/resumed output publication owner for manual
and inline generation. It retains the same reviewed plan and uses ordinary
source/history validation and immutable publication receipts for replay.
The reviewed business output is retained before fallible embedding preparation.
The existing publication-preparation owner computes and caches the vectors;
prepared output may differ from reviewed output only in embedding fields, not
instructions, generated terms, lineage, targets, timestamps or options. An
embedding failure therefore resumes publication without repeating the three
successful semantic stages. Opaque-provider windows use their actual
`window:<id>` owner and `initial_window` origin; a retirement-only result remains
a write plan even when no new entries exist.

## Source and retrieval adaptation

The native consumer receives the complete admitted single textual source chunk,
not a silently clipped history string. Current multi-chunk source-quoted recovery,
expert extraction and old retained contracts keep their existing independent
owners. A selected procedural operation never switches to the old semantic
method after a failure. A compiler request that cannot fit fails explicitly.

Production retrieves a bounded set of current same-user/version incumbents with
the existing consolidation retrieval helper. Its query is the last 4,000
characters of the current visible source, using the existing prior-knowledge
query bound. This retrieval adaptation differs from a lab case supplying a
complete small library. The exact retrieved rows are retained once, and all their
historical fingerprints are validated through the existing native lock owner.
There is no unbounded production library read or new search algorithm.

The product source adapter retains field provenance for non-content pieces.
Native prepared spans carry their actual field name (`shadow_content`,
`user_action_description`, `user_action`, or `tools_used[i]`). Inline source
views label their existing `native_tool_display` and
`native_user_action_display`; they do not reveal hidden shadow responses.
Labels remain outside exact witness text and do not assign semantic verdicts.
Content-only catalogs remain byte-identical. This presentation adaptation
prevents metadata from appearing to be an additional direct utterance, while
ordinary textual metadata and retrieval attribution continue through the same
selected method. Visual and expert inputs retain their independent capabilities.

An inline turn without visible evidence is absent from the procedural catalog,
while the original ownership/source witness still binds every window interaction.
This includes tool-only turns the native inline renderer does not expose. If the
entire visible projection is empty, code records `no_visible_native_evidence`
and an ordinary retained NOOP with no model provenance or provider turns. Hidden
shadow content does not become a replacement source. Native automatic windows
with no prepared textual spans follow the same zero-call outcome under their
actual window ownership and publication fence.

## Rolling release and rollback contracts

Fresh procedural window parents atomically declare **source-preparation version
5**, the selected method identity, `ProceduralOutput` schema and exact
organization/project/user/window/request/version scope before the first provider
call. The new reader accepts version 5 only with that bound procedural contract;
its lossless source geometry otherwise follows preparation version 3.

The serving SDK reader at `db97b093` and readers at `88accf44` and `f850e9a2`
reject preparation version 5 before
model execution or cached window publication. This deliberately prevents an old
image from reinterpreting partially completed procedural work as its old gate
and extraction pipeline. Older retained source preparations keep their original
contracts and are not relabeled as procedural work. Marker-free historical
window parents likewise retain their exact saved classic output schema. The
extractor replays that native retained output rather than interpreting it as a
fresh procedural request or redrawing its source through V8.

Prepared inline procedural outputs use **publication-preparation version 2**.
The new reader requires the actual procedural output schema and exact retained
reviewed plan. Previous readers reject version 2 before decoding or applying a
cached plan; ordinary legacy preparation version 1 remains readable. Unprepared
procedural outputs also cannot validate as the old normal playbook output shape.

This is a JSON execution-contract change, not a database DDL migration. An old
image can hold unfinished new work; it cannot finish that work. Rollback must
preserve these records and forward-drain them with a compatible image. Do not
downgrade markers, clear journals, refund attempts or rerun an old engine to make
an incompatible image finish them. Qualification must exercise these refusal and
forward-recovery paths before release.

Tests in `test_procedural_previous_readers.py` execute digest-checked public
reader functions from the serving production revision and the two previous revisions, with provider and write paths
blocked, to verify the compatibility floor. Native/inline integration tests use
real SQLite ownership/publication and scripted provider wire replies; these are
engineering compatibility checks, not a new quality comparison.


Ordinary native editors/tuners can change instruction text without updating the
inline manifest's character counts. `read_existing` is an incumbent-read adapter:
strict canonical decode first, then a read view only when each declared complete
section marker occurs exactly once, in order, and partitions all body bytes under
a valid manifest/resource graph. It never rewrites stored content, source-state
hashes, search indexes or resource bytes. Canonical new outputs still use strict
`decode`/`encode`. Ambiguous, missing, reordered or unsafe framing refuses rather
than guessing or treating malformed prefixed content as a plain rule. Native
rule-evidence exact-clause edits are covered without changing the tuner's write or
projection contracts.


Transport compatibility stays inside `transport.py`. The native client still owns
provider/model selection, credentials, fallbacks, capacity, deadlines and physical
attempt guards. A resolved stage ladder containing a single-tool native CLI or
OpenClaw provider uses one inert `return_procedural_batch` envelope, carrying all
typed declarations and an explicit terminal completion marker. This envelope is
fixed before admission and is shared by configured mixed network/CLI ladders.
Network-only MiniMax delivery keeps the selected flat function-call protocol.
Qualified Claude models use automatic tool selection where their native policy
forbids forcing a tool; plain or truncated responses remain failures. Corrective
history preserves the actual provider tool envelope and shared signed/encrypted
continuation metadata. None of these returned declarations executes a tool.

### Inline stage continuation

Inline procedural execution retains a separate revisioned checkpoint in the
actual agent run's JSON snapshot. It is not a committed output or a publication
preparation. The owned writer binds original sources/history and selected stage
profiles before inference, reserves each physical dispatch before transport,
preserves successful stages and terminal contract failures, and never refunds
the six-dispatch operation limit. Opaque window providers declare the same
version-5 source-preparation floor with an explicit inline adapter; this records
source geometry and reader compatibility, not a provider context-capacity claim.

Automatic opaque-provider windows resume these stages through their real window
worker. Manual requests have distinct UUID operation identities and currently no
background partial-stage resume endpoint: provider interruption ends that manual
operation as failed while retaining its checkpoint. A later explicit manual
request is a new operation, not recovery of that failed operation. Completed
manual output and embedding/publication recovery continue through the existing
retained-output finalizer without reissuing semantic stages.

Project admission uses the actual established work scope until storage stamps the
run row. Continuation uses the persisted row's project identity. A different
current scope cannot relabel stored preparation. Default-project SQLite tests do
not establish the nonempty-project enterprise cohort: that requires the native
project-aware storage qualification cells.
