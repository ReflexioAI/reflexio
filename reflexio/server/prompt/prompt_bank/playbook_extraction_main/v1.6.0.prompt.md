## Trigger Timing

The trigger must be the earliest observable future condition where the action
can help: the initial task class, user constraint, input state, or relevant tool
result—not the later mistake, correction, repetition, or outcome.

Write triggers as the earliest observable situation where a future agent should act differently, not as the user's later repair request or the corrective action. For example, prefer "When editing one deployment doc for an env-var/secret/port change" over "When syncing two deployment docs."

The trigger must be evaluable using only what is observable at that earliest moment — do not require facts that only emerged later in this conversation, such as identifiers the user supplied while troubleshooting or the failure of the agent's first remedy. Never narrow a trigger by "and"-conjoining such incidental details; a later-turn symptom may appear only as an "or ..." alternative that broadens matching (e.g., prefer "When a user reports they cannot log in, or says a recent password reset did not resolve their sign-in problem" over "When a user reports login trouble and provides their email address").

## Action vs avoidance framing

Write each playbook in the form that best matches its evidence:

- Use direct action language for successful, neutral, or ambiguous evidence. This is the default and covers most entries.
- Use avoidance language only when the specific rule is grounded in a clear failure pattern: user pushback, self-correction away from an approach, external refutation, or explicit dislike.
- Never write a preemptive avoidance rule for a mistake that did not occur in this trajectory — this applies per-rule, including individual avoid-bullets inside multi-rule content.

When writing an avoidance rule, start `content` with `Avoid`, `Do not`, `Don't`, or `Never`, and make the `rationale` name the observed failure pattern. Do not add a separate polarity field; downstream systems infer orientation from the wording and evidence.

When that observed failure is a **capability or environment fact that can change on its own** — a tool, API, endpoint, service, permission, or dependency that failed — begin the `rationale` with the session date shown in its `=== Session N (date: YYYY-MM-DD) ===` header, in the form `As of YYYY-MM-DD, ...`. Use the header date verbatim; never infer, round, or invent one, and omit the prefix entirely if no header date is present. This records *when* the capability was observed in that state, so a later reader can weigh how old the observation is.

Date only this class of claim. A rule grounded in a user's preference, a stated policy, a standing rule, or any constraint that does not depend on a changeable external system takes no date — those are not observations that go stale. Adding the date changes `rationale` only: `content` keeps the same wording and the same force it would otherwise have.

## Structuring multi-aspect content

When the guidance for a playbook covers multiple steps or sub-aspects of a task, write `content` as a short set of rules grouped by sub-goal, rather than one dense sentence. Phrase each rule as a clear action (do) rule, or as an avoidance rule (`Avoid`/`Do not`/`Don't`/`Never`) when it names a failure to steer around. Keep it minimal — only the rules the evidence supports; a single-point playbook stays a single rule. Do not force structure where the guidance is atomic.
